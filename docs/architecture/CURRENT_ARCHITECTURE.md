# CueKoda 0.6.0 architecture audit

Source reference `a31211a41b5c016b5191eaccc4046183f25a55ad` was the head of `origin/main` when this audit started. PR #40 overlays measurement hooks on that source. The local main and Beatport branch were ahead on a different lineage and are outside this reference.

| Area | Implementation and migration considerations |
|---|---|
| Processes | `src/main/main.ts` owns the Electron window, native dialogs, store, watchers, queue, updater and export writes. `src/main/preload.ts` exposes the typed `CueKodaApi` over specific invoke/send/event channels. `src/renderer` is TypeScript, HTML and CSS under Chromium. |
| Isolation and IPC | BrowserWindow uses a sandbox, context isolation and disabled renderer Node integration. Navigation and additional windows are blocked. `src/shared/validation.ts` validates export paths/options. Other handlers accept a wider range of renderer arguments, including local paths. Audit path authorization alongside any new desktop bridge. |
| Jobs | `queue.ts` maintains pending jobs, reusable worker-thread slots and monotonic request IDs. It handles pause, dynamic concurrency, failed workers and active cancellation by disposing of the worker. Each worker can open FFmpeg subprocesses and an isolated Node ONNX runner. Child-process cleanup matters separately from worker cancellation. Progress and summaries travel through IPC. Queued/interrupted library records restart on launch. |
| Decode and metadata | `decode.ts` starts FFmpeg with one audio decode/filter thread, outputs whole mono float32 PCM, parses EBU R128 over the original channels, detects short/partial audio, and checks MP3 gapless markers. `analyzer.ts` limits full analysis to 20 minutes and retries on the left channel when mono cancels. `music-metadata` reads tags. Content hashing and pre/post file revision checks prevent a replaced file from silently reusing analysis. |
| Tempo and downbeats | `analyzer.ts` decimates audio, builds frequency-band/onset envelopes with `dsp.ts` and fft.js, tests DeepRhythm tempo proposals against a verifying grid, then uses Essentia WASM as fallback. `rhythm.ts` refines pulse/phase with onset comb fits, alternative tempos, entrance and bass evidence, and bar accents. `tempomap.ts` models tempo changes, and `beatgrid.ts` exposes variable-grid beats to the UI/export. |
| Tonality | `key.ts`, `neuralKey.ts` and `analyzer.ts` combine profile-dependent Essentia or OpenKeyScan evidence, segment votes, confidence and harmonic labels. Export notation has its own mapping. Overrides can impose BPM, phase or key. |
| Voice / models | `neuralModels.ts` forks `neuralRunner.ts` and sends typed arrays over Node IPC. The ONNX CPU provider hosts DeepRhythm, OpenKeyScan and MusiCNN. MusiCNN also has a TensorFlow.js WASM fallback and a spectral heuristic from `vocals.ts`. Licenses and provenance are in `models/neural/README.md` and the weights directories. Preserve model assets, tensor preprocessing and fallbacks together. |
| Structure and cues | `structure.ts` uses bar features, novelty, bass, energy, repeated phrases and landmarks. `electroCue.ts` refines electronic drop/break predictions using shipped JSON models. `preparation.ts` applies a profile to shared musical features. `cues.ts` selects, ranks and spaces candidates; `loops.ts` proposes grid-aligned loops. `merge.ts` preserves applicable locked/manual cues, accepted loops, edited vocals and overrides. |
| Loudness, energy and identity | FFmpeg EBU R128 supplies integrated loudness, LRA and true peak; `analyzer.ts` derives RMS/crest metrics and `energy.ts` derives relative track/section energy. `fingerprint.ts` and `duplicates.ts` compare musical fingerprints and file hashes to distinguish duplicates and related versions. |
| Mixing | `mix.ts` proposes usable cue-derived entry and exit spans, including vocal overlap context. `matching.ts` uses harmonic/tempo/energy compatibility, `transition.ts` calculates alignment and fade preview, and `setorder.ts` heuristically orders sets. |
| Library and playback | `renderer.ts` maintains selection, search, sorting, crates and all visible DOM rows. Large-list rendering is not virtualized. HTML audio elements handle playback via local file URLs, with additional deck/preview and Web Audio behavior. `waveform.ts` uses HiDPI 2D Canvas. `peaks.ts` builds four-band peaks for zoom; main serves them through IPC with a 12-entry in-memory cache. |
| Persistence | `store.ts` debounces JSON writes and uses same-directory temp/rename. Library schema v2 splits the index and per-track results and can read v1 inline results. Settings, crate, learning and reference stores are separate. The analysis worker validates a cache keyed by content, engine version, relevant options and model availability. Manual edits live in library results independently from the analysis cache. |
| Interchange | `core/import/collection.ts` reads Rekordbox XML and Traktor NML with xmldom. `core/export` writes XML/NML plus M3U8 for playlist-only targets. Time offsets, AutoGrid, memory cues, loops, volume/path mapping and transient spacing are format-specific. Existing M3U8 behavior is export. |
| Distribution | electron-builder produces macOS arm64/x64 DMGs and Windows x64 NSIS. The build workflow is tied to main and publishes GitHub releases. The updater checks GitHub release assets, size and SHA-256 before launching the Windows installer or macOS swap helper. The digest and artifact share the same trust origin. See [security and distribution](SECURITY_AND_DISTRIBUTION.md). |
| Validation | Unit cases exercise queue, persistence, grid, interchange, preparation and transport helpers. End-to-end tests synthesize songs, smoke opens Electron, and evaluator scripts report annotations, genre and coverage. Test counts are available. Line and branch coverage were not collected. |

## Measured bottlenecks and open questions

The synthetic library grew from about 453 MiB of sampled aggregate RSS and 362 ms to renderer readiness with zero tracks to 1,013 MiB and 805 ms with 10,000 missing synthetic records. This matches a code path that renders all rows and performs startup path checks. A profile is needed to apportion the difference among file checks, IPC cloning, DOM creation and layout.

The smoke fixture verified that two analyses subsequently reused cache. The varying outcomes of the rhythm gate merit investigation before substituting the analysis engine. The benchmark reports the JS process CPU for the rhythm job and does not attribute that cost to individual DSP stages or native children. See [measurements](../benchmarks/RESULTS.md).
